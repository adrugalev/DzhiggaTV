# Обновление через GitHub Releases

С 1.2.12 при запуске и затем в фоне удаляются завершённые рабочие каталоги обновлений, версия которых ниже установленной. Сохраняются текущая и более новые версии, свежие/незавершённые загрузки, каталоги работающих установщиков и неизвестные файлы. Очистка ограничена проверенными дочерними каталогами `updates`; переходы по junction/symlink запрещены. База, настройки, плейлисты и логотипы не участвуют в очистке.

Начиная с 1.0.13 плеер проверяет публичные стабильные Releases репозитория `adrugalev/DzhiggaTV` при запуске, раз в 15 минут и при возвращении в окно (не чаще раза в 5 минут). Проверка выполняется в фоне. При ошибке сети просмотр продолжается без всплывающих сообщений.

Если вышла новая версия, блок номера версии получает бирюзовую подсветку, подпись «ОБНОВЛЕНИЕ» и стрелку. Нажатие открывает описание выпуска с GitHub и кнопку «Обновить и перезапустить». Обычное нажатие без доступного обновления открывает историю версий. В истории всегда есть кнопка «Проверить обновления» для немедленной проверки, независимо от фонового интервала. С версии 1.2.7 проверка проходит в этом же окне: при отсутствии обновлений появляется небольшая надпись «Версия актуальна. Новых версий не найдено»; с 1.2.8 она размещена слева от кнопки. Окно загрузки открывается только при обнаружении новой версии. Ошибка сети показывается рядом с кнопкой и не выдаётся за отсутствие обновлений; закрытие истории отменяет незавершённую проверку.

Загрузка показывает проценты и мегабайты, её можно отменить. Текущий просмотр продолжается до окончания загрузки. Установщик запускается только после проверки размера, SHA-256 и соответствия его версии тегу выпуска. Затем плеер сохраняет настройки, закрывается, отдельный установщик ждёт завершения именно этого процесса, заменяет приложение и открывает новую версию с прежней папкой данных. Пароли, плейлисты и другие пользовательские данные на GitHub не отправляются.

Используется управляемый установщик из `scripts/build-managed-installer.ps1`. Старые выпуски до 1.0.13 нужно один раз обновить обычным установщиком. Переносимая копия при первом обновлении устанавливается в `%LOCALAPPDATA%\Programs\DzhiggaTV`; её папка данных передаётся новой версии. Существующая установка в нестандартной папке обновляется на месте, если в ней есть манифест установщика.

## Автоматический выпуск после загрузки исходников

### Небольшие обновления с 1.0.16

Начиная с 1.0.16 установленный плеер предпочитает `DzhiggaTV-Update-x64.zip`, когда этот пакет меньше полного установщика. Это дельта на уровне файлов: в ZIP находятся только новые или изменённые файлы, а манифест описывает все файлы целевой версии. Неизменившиеся .NET и libmpv берутся из установленной копии и проверяются по размеру и SHA-256. Точный размер зависит от изменений; при смене .NET или видеодвижка пакет может быть большим.

Плеер проверяет SHA-256 скачанного ZIP и заранее собирает полный локальный пакет, проверяя каждый файл по манифесту. Подготовка выполняется в фоне, текущая установка не меняется. Отмена удаляет частичный пакет. При недоступной, повреждённой или неподходящей дельте плеер автоматически переходит на полный установщик. Подготовленный архив повторно проверяется отдельным updater после завершения процесса плеера. Установка использует прежнюю замену staging/backup; версия EXE проверяется до замены папки.

Updater запускается из отдельной временной копии уже установленного runtime, поэтому его запуск не блокирует заменяемые файлы и не требует скачивания ещё одной .NET. Для подготовки требуется свободное место на диске примерно как для полной распаковки приложения и временного runtime. Пользовательский профиль, плейлисты и настройки остаются отдельно.

Версии 1.0.15 и старше не умеют читать дельты: **переход на 1.0.16 один раз скачивает полный установщик**. В переносимой копии без метки установщика также применяется полный установщик. Пропуск нескольких выпусков допускается, если все повторно используемые файлы совпадают с целевыми; иначе автоматически загружается полный пакет.

При сборке `scripts/build-release.ps1` получает небольшой манифест последнего стабильного выпуска с GitHub, проверяет опубликованную SHA-256 и сравнивает его с новой portable-сборкой. Если предыдущий выпуск ещё не содержит манифеста или база недоступна, выпускаются полный установщик и новый манифест; дельта появится в следующем выпуске с доступной базой. Для локальной проверки можно передать `-BaselineManifest <path>`. Дельта, которая не экономит трафик по сравнению с полным portable ZIP, не публикуется.

Артефакты `outputs/updates-<version>`: `DzhiggaTV-win-x64.manifest.json`, его `.sha256`, а при наличии выгодной дельты — `DzhiggaTV-Update-x64.zip` и его `.sha256`. GitHub Actions загружает все эти файлы в черновик и публикует выпуск только после проверки всех вложений. Манифест обязателен, даже если в текущем выпуске нет дельты: он нужен для следующего выпуска.

В репозитории настроен GitHub Actions `Build and publish Windows release`. После каждого push в `main` он читает номер из `Directory.Build.props`. Если такого опубликованного выпуска ещё нет, Actions собирает приложение и установщик на Windows, запускает проверки, проверяет реальную распаковку и совпадение версий, загружает EXE с SHA-256 и публикует стабильный Release как Latest.

Для следующего выпуска достаточно увеличить `<Version>` (например, до `1.0.17`), добавить описание в `ReleaseNotesWindow.cs` и загрузить исходники в `main`. Вручную создавать тег, релиз или загружать установщик больше не требуется. Текст для пользователей берётся из записи этой версии в истории изменений.

Повторный push с уже опубликованным номером ничего не перезаписывает. При ошибке тестов публикации нет; при обрыве загрузки выпуск остаётся черновиком и не предлагается плеером. Неудачный запуск можно повторить через Actions → Re-run jobs. Также доступен Run workflow для ручного запуска на `main`. Более старый номер не вытеснит новый Latest.

Секреты вручную добавлять не нужно: используется временный `GITHUB_TOKEN` с правом `contents: write`. Если Actions отключены в настройках репозитория, их нужно включить. Готовые установщик и SHA-256 прикрепляются к GitHub Release; локальная команда сборки по-прежнему оставляет их в корне проекта.

## Ручной выпуск при необходимости

1. Увеличьте `<Version>` в `Directory.Build.props`, например до `1.0.17`. Версия установщика наследуется из этого же файла. Добавьте запись в историю изменений.
2. Выполните `scripts\build-release.ps1`. Скрипт запускает проверки, собирает portable и установщик; готовые `DzhiggaTV-Setup-x64.exe` и `DzhiggaTV-Setup-x64.exe.sha256` находятся в корне проекта. Одинаковый номер повторно не используйте.
3. На GitHub откройте **Releases → Draft a new release**. Укажите тег `v1.0.17`, добавьте понятное пользователю описание изменений, приложите установщик с `.sha256` и все файлы из `outputs/updates-<version>` и опубликуйте стабильный выпуск как Latest. Черновики и prerelease не предлагаются пользователям.

Плеер читает готовый опубликованный Release, поэтому после push нужно дождаться зелёного результата Actions. В релизе нужен сам установщик, автоматически добавляемые архивы исходников для обновления не подходят. Публичный GitHub API обычно возвращает SHA-256 вложения; отдельный `.sha256` служит совместимым запасным источником проверки. Файл должен содержать SHA-256 и имя выбранного установщика.

При открытом плеере подсветка появится после очередной проверки (до 15 минут). Кнопка в истории запускает проверку сразу. Ограничение запросов GitHub может временно отложить проверки; рядом с кнопкой появится понятное сообщение.

## Проверки

`tests/DzhiggaTV.Update.Tests` проверяет числовые версии, исключение draft/prerelease, выбор вложения, SHA-256, повторное использование проверенной загрузки, отмену, ограничение размера, привязку к репозиторию, допустимые CDN-перенаправления, ETag и ограничение частоты запросов GitHub. Проверки не публикуют релизы и не скачивают исполняемые файлы из сети.

Проверки установщика проверяют также параметры автоматического обновления, сохранение пути профиля, ожидание процесса с защитой от повторного использования PID и отмену ожидания. Замена папки использует существующий механизм staging/backup с возвратом предыдущей папки при ошибке. При сбое окно обновления предлагает повторить попытку или открыть плеер.
